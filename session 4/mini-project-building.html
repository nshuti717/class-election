2 New pieces you will need

Everything your project needs that the Shopping List did not use. Each piece is explained on a small example from a contacts app, not from any project. Most projects need the first five; the others depend on which project you choose. Already did Shopping List+? The first five will be a recap.

🧠 Showing a message instead of an empty screen

What goes on the screen can depend on the data. condition ? a : b works for whole widgets: a message when the list is empty, the list otherwise.

Expanded(
  child: shown.isEmpty
      ? const Center(child: Text('No contacts yet'))
      : ListView.builder(
          itemCount: shown.length,
          itemBuilder: (context, index) {
            final contact = shown[index];
            return ListTile(
              title: Text(contact.name),
              onTap: () => open(contact),
              onLongPress: () => deleteContact(contact),
            );
          },
        ),
)
🧠 Finding things in a list

where gives every item that matches a test. isNotEmpty tells you if there was one, first gives you the first one, and indexOf tells you its position. Comparing in lower case makes aline and Aline the same.

final matches = contacts.where((c) => c.name.toLowerCase() == 'aline');
if (matches.isNotEmpty) {
  final aline = matches.first;
  final position = contacts.indexOf(aline);
  print('Aline is at position $position');
}
🧠 Filters

Never change your real list to filter it, or the hidden items are lost. Keep the chosen filter in your State, build a second list (shown) from the real one in build, and give shown to the ListView. ChoiceChips let the user choose.

String filter = 'All';
final shown = filter == 'Favourites'
    ? contacts.where((c) => c.favourite).toList()
    : contacts;
ChoiceChip(
  label: const Text('Favourites'),
  selected: filter == 'Favourites',
  onSelected: (_) {
    setState(() {
      filter = 'Favourites';
    });
  },
)

Careful: with a filter on, row 0 on the screen is not item 0 of your real list. To change or delete, use the item itself (contacts.remove(contact)), never the row's index.

🧠 Undo

To put something back exactly where it was, remember its position before removing it. A SnackBar can carry one button, called an action.

void deleteContact(Contact contact) {
  final position = contacts.indexOf(contact);
  setState(() {
    contacts.remove(contact);
  });
  ScaffoldMessenger.of(context).showSnackBar(
    SnackBar(
      content: Text('${contact.name} deleted'),
      action: SnackBarAction(
        label: 'Undo',
        onPressed: () {
          setState(() {
            contacts.insert(position, contact);
          });
        },
      ),
    ),
  );
}
🧠 A second screen

A new screen is just another widget class. Navigator.push opens it on top, and Navigator.pop(context) goes back (so does the back arrow Flutter adds). The data goes in through the constructor, with required, like HomeScreen(title: ...). initState runs once when the screen opens: use it to fill the fields. .then runs when the user comes back, so the first screen can redraw with the changes.

Opening it:

Navigator.push(
  context,
  MaterialPageRoute(builder: (context) => ContactScreen(contact: contact)),
).then((_) {
  setState(() {});
});

The screen itself:

class ContactScreen extends StatefulWidget {
  const ContactScreen({super.key, required this.contact});

  final Contact contact;

  @override
  State<ContactScreen> createState() => _ContactScreenState();
}

class _ContactScreenState extends State<ContactScreen> {
  final nameController = TextEditingController();

  @override
  void initState() {
    super.initState();
    nameController.text = widget.contact.name;
  }

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('Contact')),
      body: Column(
        children: [
          TextField(controller: nameController),
          FilledButton(
            onPressed: () {
              widget.contact.name = nameController.text.trim();
              Navigator.pop(context);
            },
            child: const Text('Save'),
          ),
        ],
      ),
    );
  }
}

The contact's name is changed here, so in the model it cannot be final. And when you change your model, do a hot restart, as in step 8.

🧠 Coming back with an answer

An "add" screen usually sends the new thing back to the screen that opened it. Navigator.pop can carry a value, and .then receives it. If the user pressed the back arrow instead, the value is null.

Navigator.push(
  context,
  MaterialPageRoute(builder: (context) => const NoteScreen()),
).then((result) {
  if (result != null) {
    setState(() {
      notes.add(result);
    });
  }
});

And on the second screen, when the user taps Save:

Navigator.pop(context, 'Buy stamps');
🧠 Reading a number safely

int.parse crashes on 5k. int.tryParse gives null instead, so you can refuse it with a message. It still accepts -3, so check the number is above zero too.

final amount = int.tryParse(amountController.text.trim());
// '5000' gives 5000   '5k' gives null   '-3' gives -3
🧠 Are you sure?

Before something that cannot be undone, ask. showDialog opens a box over the page; Navigator.pop(context) closes it.

showDialog(
  context: context,
  builder: (context) {
    return AlertDialog(
      title: const Text('Delete everything?'),
      actions: [
        TextButton(
          onPressed: () => Navigator.pop(context),
          child: const Text('Cancel'),
        ),
        FilledButton(
          onPressed: () {
            setState(() {
              notes.clear();
            });
            Navigator.pop(context);
          },
          child: const Text('Delete'),
        ),
      ],
    );
  },
);
🧠 A grid

Like ListView.builder, but in rows of several boxes. crossAxisCount is how many per row.

Expanded(
  child: GridView.builder(
    gridDelegate: const SliverGridDelegateWithFixedCrossAxisCount(
      crossAxisCount: 4,
    ),
    itemCount: tiles.length,
    itemBuilder: (context, index) {
      return Card(child: Center(child: Text(tiles[index])));
    },
  ),
)
🧠 A yes / no switch

A row with a label and an on/off switch. Keep its value in your State.

SwitchListTile(
  title: const Text('Urgent'),
  value: urgent,
  onChanged: (value) {
    setState(() {
      urgent = value;
    });
  },
)
🧠 Bars and styled boxes

LinearProgressIndicator draws a bar filled from 0.0 (empty) to 1.0 (full): perfect for percentages. Container with a BoxDecoration gives any box a colour and rounded corners.

const LinearProgressIndicator(value: 0.44, minHeight: 12)
Container(
  padding: const EdgeInsets.all(16),
  decoration: BoxDecoration(
    color: Colors.green,
    borderRadius: BorderRadius.circular(16),
  ),
  child: const Text(
    'Balance: 10,000 RWF',
    style: TextStyle(color: Colors.white, fontSize: 22),
  ),
)

3 Requirements for every project

  1. At least two screens, with data going from one to the other (for example a list screen and an add or details screen).
  2. A model class for your main data, with sample data so the app is never empty on its first run.
  3. The rules live in functions, outside build.
  4. Every input is checked. Wrong input is refused with a clear message, and nothing changes.
  5. The screen always shows the current data. Every change appears straight away, on every screen.
  6. A way to fix mistakes: undo, edit or delete, whichever fits your app.
  7. No blank screens. When there is nothing to show, say so.
  8. Your own design: an app name, a theme colour, icons. Not a copy of the Shopping List.
Your repository
  • A new GitHub repository for this app, with small commits as you build.
  • A README with: the app name, which project you chose, a list of features, at least four screenshots, and your answers to your project's Think questions.

4 MoMo Wallet

BUILT ON LABS 3 · 2 · 6

A wallet like the one on every phone in Rwanda: money comes in, you send money to friends, you cash out at an agent. And the balance must never lie.

Screens

WalletThe balance in a big card, the statistics, and every transaction, newest first, with a filter.
Send moneyA phone number and an amount.
Cash outAn amount, then the exact notes the agent will hand you, then Confirm.

Requirements

  1. The wallet starts at 10,000 RWF with a few sample transactions.
  2. Each transaction shows its description, its amount, and whether it is IN (green) or OUT (red), newest first. A filter shows All, IN or OUT.
  3. Receiving money adds an IN with a description. The amount must be a whole number above 0, and the description cannot be empty.
  4. Sending money (Lab 2): the phone number must be exactly 10 digits and start with 078 or 079, and the amount must be at least 100 RWF. A refusal says which rule failed. A successful send becomes an OUT: Sent to 0788123456.
  5. Cashing out (Lab 6): the agent has notes of 5,000, 2,000, 1,000, 500 and 100 RWF, so the amount must be a multiple of 100. Before confirming, the screen shows exactly which notes you will get, biggest first. Confirm adds an OUT: Cash out.
  6. Any OUT bigger than the current balance is refused: Insufficient balance.
  7. Statistics (Lab 3): total IN, total OUT, and the lowest balance ever reached.
  8. A transaction can be deleted, with Undo, and everything is recalculated. But if deleting it would make the balance go below 0 at any point in the history, the delete is refused.
✔ Your app is done when
  • Sending to 0721234567 is refused (not 078 or 079), and so is sending 50 RWF to 0788123456.
  • Cashing out 23,700 RWF shows 5,000 × 4 · 2,000 × 1 · 1,000 × 1 · 500 × 1 · 100 × 2. Cashing out 250 RWF is refused.
  • An OUT of 1,000,000 RWF is refused, and so are 5k, 0 and -200.
  • The totals and the lowest balance are right after several transactions, and after a delete.
🤔 Think (answer in your README)
  1. Why must every check happen before any money moves? What would go wrong if one check came after?
  2. Your lowest-balance statistic needs a starting value. What did you start it at, and why not 0?
⚡ Push further
  • A 100 RWF fee on every send, shown as its own OUT.
  • A transaction details screen.

5 Class Election

BUILT ON LABS 8 · 4 · 9

The class elects its representative. Names arrive messy, every vote must count exactly once, the results must be ranked, and a tie must never become a fake winner.

Screens

VoteThe voter types their name, then taps Vote on one candidate card. The number of votes so far is shown.
ResultsEvery candidate ranked, with their votes, percentage and a bar, and a banner: the winner, or the tie.
CandidatesAdd a candidate, or remove one who has no votes yet.

Requirements

  1. Three sample candidates to start.
  2. Every name is cleaned before it is used (Lab 4), for voters and candidates: spaces removed at both ends, extra spaces between words removed, and written in Title Case.   keza  uwase  becomes Keza Uwase.
  3. A vote needs a voter name, and each voter votes only once. After cleaning, aline and  ALINE are the same voter: Aline has already voted.
  4. Results show each candidate's votes and percentage of all votes, with one decimal (44.4%), and a bar of the same size.
  5. Results are ranked (Lab 9), highest first. Whichever way you sort, you must be able to explain how it works.
  6. The banner (Lab 8) says Winner: Keza, or, when the top score is shared, Tie between Keza and Mutoni (4 votes each).
  7. Before any vote, the results say No votes yet: never NaN%.
  8. A new candidate cannot be empty or a duplicate (after cleaning). A candidate with votes cannot be removed. A Reset button clears all votes, after an Are you sure? dialog.
✔ Your app is done when
  •  aLINE  can vote once, and then Aline is refused.
  • With 4, 4 and 1 votes, the results show 44.4%, 44.4%, 11.1% and a tie banner, highest first.
  • Adding the candidate  keza  when Keza exists is refused. After a reset, the results say No votes yet.
🤔 Think (answer in your README)
  1. Why must names be cleaned before they are compared? Give an example of what goes wrong otherwise.
  2. How does your app decide between a winner and a tie? Explain it in plain words.
⚡ Push further
  • Undo the last vote.
  • A turnout figure: votes cast out of the number of students in the class, which you type in.

6 My Week

BUILT ON LABS 7 · 1 · 9

Your week of classes in one app, which keeps everything in order, adds up your hours, and warns you before two courses collide.

Screens

WeekDay chips (Mon to Fri), that day's courses in order, the day's hours, and the week's total.
Add or edit courseCourse name, day, start and end time typed as 08:00.

Requirements

  1. Sample courses on at least three days, including at least one clash.
  2. Times (Lab 1): typed as HH:MM, turned into minutes to compare and calculate, and back into text to show. 8h, 25:00, 10:75 and an end time that is not after the start are all refused with a message.
  3. Order (Lab 9): each day's courses are always shown in order of start time, even right after adding or editing one.
  4. Clashes (Lab 7): two courses on the same day clash if each starts before the other ends. A course ending at 11:00 and one starting at 11:00 do not clash.
  5. A clashing course is shown in red, with Clashes with Physics (or the names of every course it clashes with).
  6. Each day shows its total class time, like 3h 30m, and the week's total is shown at the top.
  7. A day with no courses says No classes on Wednesday.
  8. Tapping a course opens it for editing. A course can be deleted, after an Are you sure? dialog.
✔ Your app is done when
  • A day with 08:00–10:00 and 10:00–11:30 shows 3h 30m, and neither course is red.
  • Adding a course that overlaps another turns both red, naming each other. Editing a time to remove the overlap makes the red disappear on both.
  • A course added with an early start appears in the right place, not at the bottom.
🤔 Think (answer in your README)
  1. Write your clash condition in plain words. Why < and not <=?
  2. Why is it easier to store times as minutes than as text like 08:30?
⚡ Push further
  • The free time between classes: Free: 12:00–14:00.
  • A week view listing every clash of the week.

7 Battery Planner

BUILT ON LABS 11 · 1 · 9

Will your phone survive today? Plan your day hour by hour, see the exact moment the battery dies, and find the smallest charging plan that saves it.

Screens

DayEvery hour from 7:00 to 23:00: its activity, whether it charges, and the battery after that hour as a number and a bar. A banner on top.
Edit hourChoose the activity, and switch charging on or off.
ReportThe drain of each activity over the whole day, ranked.

Requirements

  1. The day runs from 7:00 to 23:00, starting at 100%, filled with Lab 11's sample day.
  2. The rules (Lab 11): each hour drains video 12%, games 15%, chat 5%, music 6%, idle 2%. A charging hour adds 20%. Every hour: subtract the drain, add 20 if it charges, then keep the battery between 0 and 100.
  3. Each hour shows its activity, a charging icon if it charges, and the battery after that hour as a number and a bar. The bar turns red under 20%.
  4. The banner says ☠ Dies at 17:00 (the first hour that ends at 0%) or Survives with 2% left. Hours after the death are shown as dead, never with a battery value.
  5. Tapping an hour opens its edit screen. Saving updates every hour, the bars and the banner straight away.
  6. The report (Lab 9): the total drain of each activity over the whole day, ranked highest first, with the hungriest activity named.
  7. Find a charging plan: a button that works out the fewest charging hours that let the phone survive, and which ones. The user can then apply that plan with one tap.
  8. A Reset button, after an Are you sure? dialog, brings back the sample day with no charging.
✔ Your app is done when
  • The sample day with no charging dies at 17:00.
  • Charging at 8:00, 11:00 and 12:00 survives with 2% left. Charging at 7:00, 8:00 and 9:00 dies at 20:00.
  • Find a charging plan answers 3 hours. The report ranks video (72%), games (60%), chat (20%), idle (6%).
🤔 Think (answer in your README)
  1. Does when you charge matter, or only how much? Use your two plans above to explain.
  2. Why must the battery be kept between 0 and 100 every hour, and not just at the end?
⚡ Push further
  • Let the user change the starting battery and the start hour.
  • Add a new activity with its own drain.

8 Bus Booking

BUILT ON WEEKEND ASSIGNMENT · LABS 10 · 6

Your weekend Bus Dispatcher, with a screen: the seat map a passenger sees when booking a ticket to Huye, paying cash, and waiting for a seat when the bus is full.

Screens

Seat mapThe route and price, a grid of 12 seats (free or taken), the seats sold and the money made.
Book a seatOpens from a free seat: the passenger's name and the cash they hand over, then their change.
Booking detailsOpens from a taken seat: who sits there, and Cancel booking.
WaitlistThe people waiting for a seat, in order, priority passengers marked.

Requirements

  1. One bus: Huye, 3,000 RWF, 12 seats, shown as a grid. Free and taken seats look clearly different. A few sample bookings to start.
  2. Tapping a free seat opens the booking screen. The name cannot be empty, and the same passenger cannot hold two seats.
  3. Paying cash (Lab 6): the passenger types the cash they hand over. It must be at least 3,000 RWF and a multiple of 100. The screen shows the change in notes, biggest first.
  4. Tapping a taken seat opens its booking details, where the booking can be cancelled after an Are you sure? dialog.
  5. The seat map shows seats sold and money made (seats sold × price), always up to date.
  6. When the bus is full, a passenger can join the waitlist, with a Priority switch (elderly, pregnant, disabled).
  7. Priority (Lab 10): a priority passenger goes ahead of every ordinary passenger on the waitlist, but behind priority passengers who joined earlier.
  8. When a booking is cancelled and someone is waiting, the first person on the waitlist moves into the free seat automatically, with a message: Frank moved into seat 4. An empty waitlist says Nobody is waiting.
✔ Your app is done when
  • Booking all 12 seats shows 12 sold and 36,000 RWF.
  • Paying 10,000 RWF shows change of 5,000 × 1 · 2,000 × 1. Paying 2,500 or 3,050 RWF is refused.
  • A priority passenger who joins after two ordinary passengers is first on the waitlist, and moves into the next cancelled seat.
  • A taken seat can never be booked a second time.
🤔 Think (answer in your README)
  1. Where exactly does a new priority passenger go on the waitlist, and how did your code find that position?
  2. Why should moving someone from the waitlist happen inside the cancel function, and not when the screen is drawn?
⚡ Push further
  • A group booking: several passengers in seats next to each other, all or none (like the weekend assignment).
  • A second route, Musanze, with its own grid.

9 Your own app

BUILT ON LAB 12 · THE BRAIN OF YOUR APP

In Lab 12 you designed the brain of your own app: its data, its commands and its rules. Now give it a body. This is the best start for your final project.

Screens

Your choiceAt least two screens. What they are depends on your app: a list and a details screen, a form and a summary, a dashboard and a history.

Requirements

  1. Start from your Lab 12 design: the same data, the same commands and the same rules. You may improve them.
  2. Your README starts with your Lab 12 comment block: the app's name, the problem it solves, its commands, and what data each changes.
  3. Every command from Lab 12 becomes something on screen: a button, a form or a tap. Nobody types commands any more.
  4. Every rule that refused a command in Lab 12 now refuses the action on screen, with a clear message.
  5. Your Lab 12 scenario (your 8 or more commands) can be played on screen, one action at a time, and ends with the same results as your Lab 12 output.
  6. At least two of: a filter, a search, undo, an Are you sure? dialog, a grid, bars.
  7. Your app is big enough for two screens. If your Lab 12 idea is too small, extend it, or choose another project.
✔ Your app is done when
  • Your README shows your Lab 12 design, and every command can be done on screen.
  • Your Lab 12 scenario, played on screen, ends with the same data as your Lab 12 output.
  • Every refused action shows a message, and nothing changes.
🤔 Think (answer in your README)
  1. Which Lab 12 command was the hardest to turn into a screen, and why?
  2. What did you change in your Lab 12 logic once it had a screen, and why?
⚡ Push further
  • Sketch the next version of your app in Figma: it may become your final project.
